# CandleLab Studio v0.2 — BatchTrace, first slice

Scope: create a batch from a saved formula version, keep that exact reference, record a production date and measured quantities, and reopen the batch later. Source: the v0.2 kickoff handoff (vault, `Projects/apps/candle/Sessions/2026-11-18 - v0.2 - Kickoff Handoff.md`) and the v0.2 section of Tasks. CurePilot, BurnMatrix, lot codes, suppliers, search, filters and batch export are out of scope.

## Implementation plan (decided before coding)

### Batch identity
- A batch has a stable `id`, a UUID made on the device (DATA-01). Ids never change and are never reused.
- Display title: the maker's optional `label` (1–40 characters after trimming), otherwise `Batch ` plus the first 8 characters of the id in capitals. There is no sequential batch number, so a restore never has to renumber batches (unlike versions, DATA-22).
- `create` is idempotent on the id: the screen picks the id once and reuses it on retry, so a double tap or a retried save never makes two batches.

### Formula and version reference
- A batch stores `formulaId` and `versionId`, set at creation from the version and never changed afterwards. `update` copies them from the stored record and ignores whatever the input says.
- Planned quantities are not copied into the batch. They are read from the source version's stored `targets` and component snapshots, which are write-once (DATA-02, DATA-08). Revising or scaling a formula creates new versions and never touches the one a batch points at.
- Measured quantities use the existing conventions: whole milligrams (DATA-05), entered as grams with at most 2 decimals, 0 g or more (V-16), optional per component, keyed by the version's `componentId`. Entries naming a component that is not a wax or oil row of the source version are refused.
- Production date: `producedOn`, a calendar date `YYYY-MM-DD` in the maker's local calendar, required. The screens refuse a date after today; the data layer checks the format only (so a device clock or time zone change cannot make stored data invalid).

### Editing and deletion
- Editable: production date, label, notes, measured weights. Each save is one transaction and adds 1 to the change counter (DATA-13).
- A batch can be deleted after confirmation. (When CurePilot and BurnMatrix link records to batches, deletion of a linked batch will be refused the same way formula deletion is.)
- **Archived source formula:** archiving only hides the formula from the active list. Its batches stay listed, open and editable, show a "Formula archived" badge, and new batches can still be made from its versions.
- **Deleted source formula:** deleting a formula is refused while any batch refers to it (DATA-12, as planned in the v0.1 Data Model). The data layer throws `DataError("in-use")` and writes nothing; the delete dialog explains that batches keep a link to their version and offers archiving instead. Deleting the batches first makes the formula deletable again. So a batch's source version always exists and history stays intelligible.

### Migration (IndexedDB schema 1 → 2)
- Schema version 2 only adds the store `batches` (key `id`; indexes `formulaId`, `versionId`, `producedOn`). Every v0.1 store keeps its key and indexes, so Dexie's upgrade moves no data (DATA-29). Drafts and meta stay as they are.
- `src/lib/db/db.ts` keeps the version 1 declaration (`SCHEMA_V1`) so a v0.1 database opens and upgrades in place.
- Tested: `tests/unit/db/upgrade.test.ts` writes the real v0.1 export (`tests/fixtures/backups/good.json`) into a database declared with the v0.1 schema, opens it with v0.2, and checks every record, the draft and meta survive and batches can be made from v0.1 versions. A manual check with a real browser profile created by the v0.1 build is recorded in the handoff.

### Backup compatibility
- Export writes **format 2** (`formatVersion: 2`, `schemaVersion: 2`, `appVersion: "0.2.0"`) with a fifth array `data.batches` and `counts.batches`. The checksum covers all five arrays.
- Restore reads **format 1 and 2**. A format 1 file (v0.1) is checked against the format 1 shape (four arrays, strict) and its checksum is verified over its data exactly as written; only then is it migrated in memory by adding an empty `batches` array and `counts.batches = 0`. A format 1 file that contains `batches`, or a format 2 file without it, is refused as damaged.
- A format 2 file is refused by the v0.1 app with "made by a newer version", as v0.1 was built to do.
- Batches are classified like measurements: new, identical (same content) or conflict. Conflicts follow the maker's "Keep this device's copy" / "Use the backup's copy" choice. Restoring the same file twice changes nothing.
- Orphan check (Step 1): a batch whose version is neither in the file nor on the device, or whose version in the file belongs to a different formula, refuses the whole file.
- "Replace everything" clears batches too; the safety backup downloaded first includes them.

### Interrupted or failed restore
- Unchanged rule, extended to the new store: the whole restore is one IndexedDB transaction over all five data stores and meta (DATA-24). If it fails or the tab closes before commit, nothing changes (DATA-25). After commit the counts of all five stores are compared with the plan; a difference is reported as an error, never success (DATA-26). Re-running is safe (DATA-27). Tested with a failure injected after the batches store is written and with a stale plan.

### Known gap (inherited from v0.1)
- The orphan check compares against ids on the device even when the maker then chooses "Replace everything". A hand-edited file with a valid checksum could therefore restore a batch or measurement whose version was only on the device. App-made files are always self-consistent (one read transaction). Recorded for v0.3.
