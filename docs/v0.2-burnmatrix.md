# CandleLab Studio v0.2 — BurnMatrix

Scope: makers record burn tests of a batch. A session is one dated test on one batch. In it, one or more candles burn side by side, each with its own wick. Each candle gets per-burn measurements and observations, plus cold and hot throw notes. Sessions hold photos and the maker's own conclusion. Sessions can be compared side by side and exported as a printable report and a CSV. The app records observations only: it never says a candle passed, failed, is safe or is cured. Source: the v0.2 kickoff handoff and the v0.2 section of Tasks (vault), with the owner-approved defaults below. Built on CurePilot (`docs/v0.2-curepilot.md`).

Out of scope: scent panels (v1.0), defect tracking (CandleFix, v0.3), lot codes, suppliers, search and filters, PDF libraries, cloud photo storage.

## Decisions agreed with the owner

- **Sessions:** one dated test on one batch, burning one or more candles side by side, each with its own wick (free text or a wick material from the library). Each burn is logged per candle: duration, weight before and after, melt pool, flame, soot and notes. Cold and hot throw notes are per candle.
- **Photos:** stored on the device in IndexedDB and included in backups. Each is shrunk to about 1600 px JPEG when added, up to 12 per session. The backup page shows the file size.
- **Report export:** no PDF library. A printable report page (browser Print / Save as PDF) for one session or a comparison, plus a CSV of the measurements.
- **Comparison:** the candles of one session side by side, and up to 4 sessions across batches.
- **Planned burn tests:** a session can link to a CurePilot `burnTest` milestone. Saving a linked session marks that milestone done on the session date.
- **Batch delete:** refused with `DataError("in-use")` while the batch has burn sessions.
- **No verdicts:** no pass or fail. The maker writes their own conclusion.
- Branch `feat/v0.2-burnmatrix`, stacked on `feat/v0.2-curepilot`.

## Data model

Types in `src/lib/types.ts`, schemas in `src/lib/schemas/burn.ts`.

### `BurnSession` (store `burnSessions`)

```
BurnSession = {
  id: string               // UUID chosen by the screen; create is idempotent on it
  batchId: string          // fixed at creation
  testedOn: string         // YYYY-MM-DD, local calendar
  label?: string           // 1 to 60 characters after trimming
  milestoneId: string | null   // a burnTest milestone of the batch's cure plan (soft link, below)
  candles: BurnCandle[]    // 1 to 8
  conclusion?: string      // the maker's own words, up to 2000 characters
  notes?: string           // up to 2000 characters
  createdAt, updatedAt: string
}
BurnCandle = {
  id: string               // UUID, stable inside the session
  label: string            // 1 to 40 characters ("Candle 1", "A", "CD-10")
  wick: { materialId: string | null, name: string }   // name 1 to 80 characters
  burns: BurnRecord[]      // 0 to 40, in the order they happened
  coldThrow?, hotThrow?, notes?: string   // up to 2000 characters each
}
BurnRecord = {
  id: string               // UUID, stable inside the candle
  durationMin: number      // whole minutes, 1 to 1440
  weightBeforeMg?: number  // whole mg, 1 up to the weight limit
  weightAfterMg?: number   // whole mg, 0 up, not above weightBeforeMg
  meltPoolDiameterMm?, meltPoolDepthMm?, flameHeightMm?: number   // whole mm, 0 to 500
  soot?: "none" | "light" | "moderate" | "heavy"
  notes?: string           // up to 2000 characters
}
```

- **Wick:** the editor sends either a library wick (`{ materialId }`) or free text (`{ text }`). For a library wick the data layer checks that the material exists and is a wick, and stores its name as a snapshot. When a session is saved again and a candle's material is unchanged, the stored name is kept. That way a report keeps the name used at the time, as versions do for formula materials. Materials are never hard-deleted (archive only), but the restore step still treats `materialId` as informational, as it does for version materials.
- **Burns** carry no date of their own: the session is the dated unit. Burn numbers on screen are positions in the array.
- **Dates:** the data layer checks the format only. The screens refuse a test date in the future or before the batch's production date. That is the same split as for the batch production date, so moving a batch date never has to rewrite sessions.
- Optional text is trimmed and stored as absent when blank (DATA conventions). Every number is an integer: weights are typed in grams (up to 2 decimals) and parsed to milligrams with `@/lib/gramguard`'s `parseFixed`.

### `BurnPhoto` (store `burnPhotos`)

```
BurnPhoto = {
  id, sessionId: string
  mimeType: "image/jpeg"
  width, height: number    // pixels, 1 to 1600
  byteLength: number       // 1 to 1 MiB
  sha256: string           // of the bytes, lowercase hex
  caption?: string         // 1 to 80 characters
  bytes: Uint8Array        // the JPEG
  createdAt: string
}
```

- **Write-once:** a photo is added or deleted, never edited. That keeps restore conflicts on photos to the impossible case of two different photos sharing one UUID.
- **Bytes as `Uint8Array`**, not `Blob`. It converts to and from base64 synchronously, so backup code can convert inside a Dexie transaction, which must not await anything other than Dexie. It validates with a plain `instanceof` check, and it works the same in fake-indexeddb. Screens make an object URL with `new Blob([bytes], { type })` and revoke it on unmount.
- **Limits:** at most 12 photos per session (`MAX_SESSION_PHOTOS`), each at most 1 MiB (`MAX_PHOTO_BYTES`) and 1600 px on its longest side (`MAX_PHOTO_DIMENSION`). The data layer refuses a 13th photo with `invalid`. A merge restore can still bring a session above 12 (two devices that each added photos to the same restored session). The screens then show every photo and do not offer Add.

## Photos

Preparation (`src/lib/photos`, browser only):

1. Refuse files that are not `image/*` or that exceed 40 MiB before decoding.
2. Decode with `createImageBitmap(file, { imageOrientation: "from-image" })`, so the camera's EXIF orientation is applied.
3. Draw at most 1600 px on the longest side (never enlarged) on a canvas and encode JPEG at quality 0.85. If the result exceeds 1 MiB, step down to 0.75, 0.65 and 0.55, then try again at 1200 px. If it is still too big, refuse.
4. Re-encoding drops all metadata, including GPS location. This is intended and is stated in the design for privacy.

Typical result: 200 to 500 KB per photo, so a full session of 12 is about 3 to 6 MB.

**Storage full:** a Dexie write that fails with `QuotaExceededError` (also when wrapped by Dexie) becomes `DataError("storage-full")` instead of the generic `storage`. When adding a photo, the screen says that the device is out of space for this site. It tells the maker that nothing was lost, that deleting photos or making a backup and removing old sessions frees space, and that the photo was not added. Every other repository maps the same error the same way, so a full device during an ordinary save gets the same message. Before adding, the photo section shows `navigator.storage.estimate()` usage when the browser offers it. That is informational only.

**Thumbnails** are not stored: the gallery shows the stored JPEG scaled by CSS (`object-fit: cover`, `loading="lazy"`), and the larger view shows it at its own size. 12 photos of about 400 KB decode quickly. Storing a second copy would double the storage and the backup.

## Planned burn tests: the milestone link

`milestoneId` is a **soft link** to a `burnTest` milestone in the batch's cure plan.

| Event | Effect |
| --- | --- |
| Session saved (create or update) with a link | Same transaction: the data layer checks that the milestone is a `burnTest` in this batch's plan and that no other session links to it, then sets the milestone's `doneOn` to the session's `testedOn` (no write when already equal). One counter bump for the whole save. |
| Session date changed, still linked | The milestone's `doneOn` moves to the new date. |
| Link removed, or moved to another milestone | The old milestone stays as it is (done stays done). The maker can mark it open from the batch page. Nothing hidden is undone. |
| Milestone marked open (Undo) on the batch page | Allowed. The link stays. The next save of the session marks it done again. |
| Session deleted | The milestone stays as it is. |
| Milestone removed from the plan, or its kind changed from `burnTest` (`curePlans.save`) | Same transaction: `milestoneId` is set to null on the sessions that linked to it. |
| Cure plan deleted (`curePlans.delete`) | Same transaction: every session of that batch loses its link. |
| Batch deleted | Not reachable: refused while sessions exist. |
| Restore | Not part of the orphan check. A merge that keeps the device's copy of a cure plan can leave a link that no longer resolves. Screens read the link through `burnSessions.get`, which returns `milestone: null` when it does not resolve, and the editor shows the session as not linked. Saving the session then stores `milestoneId: null`. A write never stores an unresolvable link. |

One session per milestone: a planned test is one test. The editor offers the batch's `burnTest` milestones (`burnSessions.burnTestOptions`), showing the ones linked to another session as taken.

## Storage: IndexedDB schema 4

```
version(1)  v0.1 stores (unchanged)
version(2)  + batches: "id, formulaId, versionId, producedOn"
version(3)  + curePlans: "id"
            + productionPlans: "id, formulaId, versionId, plannedOn, batchId"
version(4)  + burnSessions: "id, batchId, milestoneId, testedOn"
            + burnPhotos: "id, sessionId"
```

Schema 4 only adds two stores, so the upgrade moves no records (DATA-29). IndexedDB reports version 40. A schema 3 (CurePilot) database opens with everything intact and two empty new stores. `milestoneId` is null on unlinked sessions, and IndexedDB leaves those out of the index, which is what the "one session per milestone" lookup wants. Tested in `tests/unit/db/upgrade.test.ts` from a real schema 3 database (with batches, a cure plan and a production entry), and with a real browser profile (see the handoff note).

## Writes and the change counter

Every repository write is one transaction that includes `meta` and adds 1 to `changesSinceBackup` (DATA-13):

- `burnSessions.create / update / delete`. The milestone write and the photo cascade are in the same transaction, with one bump.
- `burnPhotos.add / delete`. The SHA-256 is computed before the transaction, because Web Crypto is not a Dexie promise.
- `curePlans.save / delete`. Clearing session links is part of the same transaction and adds no extra bump.

## Archive and delete

| Event | Burn sessions | Burn photos |
| --- | --- | --- |
| Formula archived | Unchanged. Screens show the "Formula archived" badge as for batches. | Unchanged |
| Formula deleted | Not reachable: a formula with batches cannot be deleted. | Not reachable |
| Wick material archived | Unchanged. The stored name snapshot keeps showing. The picker hides archived wicks for new choices, but a candle keeps its archived wick when saved again. | — |
| Batch deleted | **Refused** with `in-use` while it has sessions (`deletionImpact().burnSessions`). The dialog says the burn tests must be deleted first. | — |
| Session deleted (after confirmation) | Only that session. A linked milestone stays as it is. | All its photos, in the same transaction. The confirmation counts them. |
| Photo deleted (after confirmation) | Unchanged | Only that photo |

Sessions have no archive state. They are dated observations, like measurements.

## Backup format 4

- Export writes `formatVersion: 4`, `schemaVersion: 4`, `appVersion: "0.2.0"`, with `data.burnSessions` and `data.burnPhotos` and their counts.
- **Photo encoding:** in the file, a photo is `BurnPhotoBackup`: the stored record with `bytes` replaced by `dataBase64`, the JPEG as standard base64 with padding (RFC 4648 section 4). `sha256` and `byteLength` stay. Conversion is in `src/lib/backup/photos.ts` and is synchronous.
- **Checksums:**
  1. The envelope checksum is SHA-256 over the canonical JSON of the whole data section, now nine arrays, base64 strings included. It covers every photo byte.
  2. Each photo also carries the SHA-256 of its own bytes. The restore check decodes every photo and refuses the file as `invalid` when the base64 is malformed, or when the decoded length differs from `byteLength`, the hash differs from `sha256`, or the bytes do not start with the JPEG marker `FF D8 FF`. So a damaged photo is named ("photo 3f2a…: photo data does not match its checksum") and is never stored.
- **Single representation in the backup code:** everything under `src/lib/backup` handles photos in their backup form. `readDeviceData` encodes stored photos to base64, `applyRestore` decodes them when writing, and every other step compares and plans one shape. Plan classification compares photos without `dataBase64`, because `sha256` stands for the bytes: it is computed when the photo is added and verified when a file is checked.
- Restore reads formats **1, 2, 3 and 4**. Formats 1 to 3 are checked against their own strict shape and their checksum is verified over the data exactly as written. Only then are the missing arrays added empty in memory. A format 3 file with `burnSessions`, or a format 4 file without it, is refused as damaged. The CurePilot app (format 3) refuses a format 4 file as "made by a newer version".
- Classification and conflicts: sessions are compared whole (canonical JSON), photos without their bytes. Both follow the maker's keep-or-replace choice, like batches. Restoring the same file twice changes nothing. "Replace everything" clears all nine stores, and the safety backup includes them.
- **File size:** `MAX_BACKUP_BYTES` rises from 25 MB to 256 MB, so a file with photos can be restored. Export reports the file size (`ExportedBackup.sizeBytes`, UTF-8 bytes), and the backup page shows it after each export and with the device's photo count and size. An export above 256 MB is still downloaded, because a backup is never withheld, but the page warns that this app cannot restore a file that large. The whole file is held in memory while exporting and restoring (about 3 times its size at peak). That is acceptable for v0.2 and recorded as an open issue (separate photo archive in v0.3).

### Orphan checks (Step 1, refuse the whole file)

Added to the CurePilot list:

- A burn session whose batch is neither in the file nor on the device.
- A photo whose session is neither in the file nor on the device.

`DeviceIds` gains `burnSessionIds`. The refusal message counts each kind. The milestone link and the wick material are not orphan checks (above).

### Interrupted or failed restore

Unchanged: one transaction over the nine data stores and meta, a stale check inside it, and counts compared after commit. Tested with a failure injected after `burnPhotos` is written.

## Calculations (`src/lib/burnmatrix`, contract in `contract.ts`)

- A burn's **weight loss** = before − after, only when both weights are recorded.
- **Rate** in mg per hour = loss × 60 / minutes, rounded half up with BigInt (`divHalfUp`). It is shown as grams per hour with 2 decimals ("3.25 g/h").
- **Per candle:** burn count and total burn time across all burns. Total loss and average rate use only the weighed burns and their minutes. There is also the last recorded melt pool diameter, the largest melt pool depth and flame height, and the soot levels seen. Nothing is guessed from neighbouring burns.
- **Comparison model:** columns are candles grouped by session, in the order chosen. Rows are a fixed list of metrics (wick, burns, total time, total loss, average rate, melt pool, flame, soot, cold throw, hot throw). Cells are formatted text and "" where nothing was recorded. There is no ranking, colour coding or best/worst marking.
- **CSV:** RFC 4180 with CRLF and a UTF-8 BOM. There is one row per burn and one row per candle without burns. Columns: session date and label, batch, formula and version, candle, wick, burn number, minutes, weights in grams, loss, rate, melt pool, flame, soot, notes, cold and hot throw, conclusion. Cells that start with `=`, `+`, `-`, `@`, tab or CR get a leading apostrophe (formula injection). Headers come from `MESSAGES.burnCsv`. The file is named `candlelab-burn-tests-YYYYMMDD.csv`.

## Screens (wording in `MESSAGES.burn`, `MESSAGES.burnCompare`, `MESSAGES.burnPhotos` and `MESSAGES.burnCsv`, all marked `WRITTEN HERE (v0.2 BurnMatrix)` for owner review)

| Route | Screen |
| --- | --- |
| `/batches/[batchId]` | Batch page gains a **Burn tests** section: the batch's sessions (date, label, candles, photo count, link to the planned test), "Record burn test", and "Compare" for 2 or more sessions. The delete dialog explains the refusal when sessions exist. |
| `/burn-tests/new?batch=[batchId]` | Session editor (new): date (today by default), label, optional planned burn test, candles with wick (library picker or free text), burns per candle (duration, weights, melt pool, flame, soot, notes), throw notes, conclusion and notes. Field errors on blur, then Save with feedback. Photos can be added once the session is saved (they need its id). |
| `/burn-tests/[sessionId]` | Session page: everything recorded, figures per burn and per candle, the candles side by side, photos (add, view, delete), and Edit, Report, Download CSV and Delete. |
| `/burn-tests/[sessionId]/edit` | Session editor (edit). |
| `/burn-tests` | All burn tests, newest first, with a picker of up to 4 sessions to compare. Reached from the Batches page and each batch's Burn tests section. It is not in the nav, which already has five phone items. |
| `/burn-tests/compare?sessions=a,b,c` | Comparison: candles grouped by session, rows of figures and observations, each session's conclusion as written. Report and Download CSV. |
| `/burn-tests/[sessionId]/report`, `/burn-tests/compare/report?sessions=…` | Printable report: app chrome hidden in print, A4/Letter friendly, a table per session and photos at print size. It states that the observations are the maker's own and that the app does not certify anything. "Print or save as PDF" calls `window.print()`. |

Wording rules: "Burn test", "Recorded", "Observed", "Soot seen: light", "Your conclusion". The app never writes "passed", "failed", "safe", "cured", "ready", "good", "bad", "best", "recommended" or "approved", and does not colour or rank results. The messages test scans every string for these words.

## Found and fixed during testing

- The comparison table's hidden "Not recorded" labels (`sr-only`, absolutely positioned) escaped the table's own scroll region, so at 375px with 2 or more candles the page itself became wider than the screen. The scroll region is now `relative`. The e2e phone tests `burn-phone.spec.ts` cover it.
- Under jsdom, fake-indexeddb returns photo bytes as a `Uint8Array` from another realm, so `instanceof Uint8Array` failed. The byte checks now use a realm-independent test (`isUint8Array` in `src/lib/schemas/burn.ts`).
- Two earlier browser tests (`batches.spec.ts`, `schedule.spec.ts`) still expected backup format 3. They now expect 4.
