# CandleLab Studio v0.2 — CurePilot

Scope: makers set curing durations and milestones for a batch, plan burn tests and production, and see in-app reminders. Changing a date or a milestone updates the schedule. Curing is presented as scheduling information only: the app never says a candle is cured, ready, safe or finished, only that a date the maker chose has come. Source: the v0.2 kickoff handoff and the v0.2 section of Tasks (vault). Built on BatchTrace (`docs/v0.2-batchtrace.md`).

Out of scope: BurnMatrix session records, lot codes, suppliers, search and filters, push or email reminders (there is no backend).

## Decisions agreed with the owner

- Reminders are **in-app only**: a Schedule page with due and overdue items, and a count in the nav.
- Milestones are stored as **day offsets** from the batch's production date. Changing the production date moves every open milestone. A milestone already marked done keeps its done date.
- **Planned production** is a schedule entry linked to a formula version, not a batch. Batches still cannot have future dates. "Create batch" from the entry turns it into a real batch.
- Branch `feat/v0.2-curepilot`, stacked on `feat/v0.2-batchtrace`.

## Data model

### `CurePlan` (store `curePlans`)

One record per batch. Its `id` **is the batch's id**, so a batch has at most one plan without any extra index, and two devices that each planned the same restored batch meet as an ordinary restore conflict (keep or replace), not as two plans.

```
CurePlan = {
  id: string            // = Batch.id
  milestones: CureMilestone[]   // 1 to 20
  createdAt, updatedAt: string  // ISO timestamps (DATA-06)
}
CureMilestone = {
  id: string            // UUID, stable inside the plan
  kind: "cureEnd" | "burnTest" | "check"
  label?: string        // 1 to 60 characters after trimming
  offsetDays: number    // whole days after the production date, 0 to 365
  doneOn: string | null // YYYY-MM-DD the maker marked it done, or null
}
```

- **Curing duration** is the `offsetDays` of the plan's `cureEnd` milestone ("Cure time: 14 days"). A plan has at most one `cureEnd`; it may have none (only burn tests, say). This rule is inside one record, so the record schema enforces it, also on restore.
- **Planned burn tests** are `burnTest` milestones. BurnMatrix can later link a session to one by its milestone id.
- `check` is any other milestone the maker names (label required by the screens).
- Milestone ids are unique within a plan. Order on screen is by `offsetDays`, then kind, then id; the stored order carries no meaning.

### `ProductionPlan` (store `productionPlans`)

A planned production run: "make version 3 of Lavender on 2 Dec".

```
ProductionPlan = {
  id: string            // UUID, chosen by the screen, create is idempotent on it
  formulaId: string     // fixed at creation, from the version
  versionId: string     // fixed at creation
  plannedOn: string     // YYYY-MM-DD, any date (past dates are allowed: late entry, or overdue)
  label?: string        // 1 to 40 characters
  notes?: string
  batchId: string | null  // the batch made from this entry, or null while open
  createdAt, updatedAt: string
}
```

- **Create batch from an entry:** `/batches/new?version=V&plan=P`. The batch form opens with today's date (never a future date, BatchTrace rule) and the entry's label. On save, `batches.create` writes the batch and sets the entry's `batchId` **in the same transaction**. It refuses with `invalid` if the entry is already linked to another batch or names a different version, and `not-found` if the entry is gone. A retried save with the same batch id writes nothing.
- An entry with `batchId` set is done. Its `plannedOn` and the batch's `producedOn` may differ; both are shown.
- `formulaId` and `versionId` never change (as for batches). To plan another version, delete the entry and plan again.

### Why offsets, and what "recalculation" means

Nothing derived is stored. A milestone's due date is always `batch.producedOn + offsetDays`, computed when the screen reads it. So:

| Change | Effect |
| --- | --- |
| Batch production date moved | Every open milestone of that batch moves by the same number of days. Done milestones keep `doneOn`; the screens show "Done on …" and never a due date for them. No cure-plan write happens. |
| A milestone's offset changed | Only that milestone moves. If it was done it stays done. |
| Cure time changed | The `cureEnd` milestone moves. |
| Milestone added, removed | Plan saved as a whole (one transaction). New milestones start open. Existing milestones keep their `doneOn` (the editor cannot change it; marking done or open is its own action). |
| Planned production date changed | The entry moves. |
| Batch made from an entry | The entry is done and leaves the reminders. |

## Schedule states and reminders (pure logic, `src/lib/schedule`)

- "Today" is the device's local calendar date (`YYYY-MM-DD` from the local clock). Day arithmetic is done on calendar dates in UTC (`Date.UTC`), so daylight-saving changes and time zones never move a date by one.
- State of an item, given `today`:
  - **done**: milestone with `doneOn`, or production entry with `batchId`.
  - **overdue**: open and due before today.
  - **due**: open and due today.
  - **upcoming**: open and due after today.
- **Attention count** (the nav badge) = open items that are overdue or due. It is computed on the device every time the data or the date changes; nothing about reminders is stored.
- The Schedule page groups Overdue, Due today, Upcoming, and recently Done, oldest due date first (done: most recent first).

## Storage: IndexedDB schema 3

```
version(1)  v0.1 stores (unchanged)
version(2)  + batches: "id, formulaId, versionId, producedOn"
version(3)  + curePlans: "id"
            + productionPlans: "id, formulaId, versionId, plannedOn, batchId"
```

Schema 3 only adds two stores. Every earlier store keeps its key and indexes, so Dexie's upgrade moves no records (DATA-29). IndexedDB reports version 30. A schema 2 (BatchTrace) database opens with its batches intact and two empty new stores. Tested in `tests/unit/db/upgrade.test.ts` (from a real schema 2 database with batches, and from schema 1) and with a real browser profile (handoff note).

## Writes and the change counter

Every repository write is one transaction that includes `meta` and adds 1 to `changesSinceBackup` (DATA-13), as before:

- `curePlans.save(batchId, milestones)` creates or replaces the plan.
- `curePlans.setMilestoneDone(batchId, milestoneId, doneOn | null)`.
- `curePlans.delete(batchId)`.
- `productionPlans.create / update / delete`.
- `batches.create` with a production entry: one transaction, one bump.
- `batches.delete`: one transaction, one bump, including the cascade below.

## Archive and delete

| Event | Cure plans | Production entries |
| --- | --- | --- |
| Formula archived | Unchanged; milestones still appear on the Schedule page and count as reminders. | Unchanged; open entries still remind, and "Create batch" still works (BatchTrace allows batches from archived formulas). Screens show the "Formula archived" badge. |
| Formula deleted | Not reachable: a formula with batches cannot be deleted (`in-use`, BatchTrace), and cure plans belong to batches. | Open entries of that formula are deleted with it, in the same transaction. The delete confirmation counts them (`deletionImpact().productionPlans`). An entry with a batch cannot exist without that batch, which already blocks the delete. |
| Batch deleted | The batch's cure plan is deleted with it (same transaction). The confirmation says how many milestones go. | An entry that made this batch becomes open again (`batchId` back to null): the run it planned is no longer recorded. The confirmation says so. |
| Production entry deleted | — | Only the entry. Its batch, if any, is untouched. |

The BatchTrace note expected linked batch deletion to be refused once CurePilot existed. That stays the rule for BurnMatrix test records, which are observations. A cure plan is the batch's own schedule, with no meaning without it, so it goes with the batch after confirmation.

## Backup format 3

- Export writes `formatVersion: 3`, `schemaVersion: 3`, `appVersion: "0.2.0"`, with `data.curePlans` and `data.productionPlans` (and their counts). The checksum covers all seven arrays.
- Restore reads formats **1, 2 and 3**. Formats 1 and 2 are checked against their own strict shape and their checksum is verified over the data exactly as written; only then are the missing arrays added empty in memory (format 1: batches, cure plans, production entries; format 2: cure plans and production entries).
- A format 2 file with `curePlans`, or a format 3 file without it, is refused as damaged. The BatchTrace app (format 2) refuses a format 3 file as "made by a newer version".
- Classification and conflicts: cure plans and production entries are compared whole (canonical JSON) and follow the maker's keep-or-replace choice, like batches. Restoring the same file twice changes nothing.
- "Replace everything" clears all seven stores; the safety backup includes them.

### Orphan checks (Step 1, refuse the whole file)

- A cure plan whose batch (its `id`) is neither in the file nor on the device.
- A production entry whose version is neither in the file nor on the device, or whose version in the file belongs to another formula.
- A production entry with a `batchId` that is neither in the file nor on the device, or that names a batch in the file made from a different version.

`DeviceIds` gains `batchIds`. The refusal message counts each kind.

The inherited gap stays recorded for v0.3: the orphan check accepts ids that are only on the device even when the maker then chooses "Replace everything". App-made files are always self-consistent.

### Interrupted or failed restore

Unchanged: one transaction over the seven data stores and meta, stale check inside it, counts compared after commit. Tested with a failure injected after the `productionPlans` store is written.

## Screens (follow BatchTrace patterns; wording in `MESSAGES.schedule`, marked for owner review)

- **Batch detail:** a Curing section. Without a plan: "Add a cure plan". With one: cure time and planned cure end, then the milestones with due date, state and a Done / Undo button. "Edit plan" opens the cure-plan editor (cure time in days, burn tests and other milestones with day offsets; field errors on blur; Save with feedback).
- **Formula page and version view:** "Plan production" next to "Create batch".
- **Planned production:** create and edit (date, label, notes), with "Create batch" on the entry.
- **Schedule page** `/schedule`: Overdue, Due today, Upcoming, Done; each row links to its batch or entry.
- **Nav:** a Schedule entry with the attention count (hidden at 0; its accessible name includes the count).
