# v0.3 CandleFix — design and implementation plan

2026-11-28. Lead design for the CandleFix slice (`docs/BUILD-STATE.md`, vault `Projects/apps/candle/Tasks.md` v0.3).
Branch `feat/v0.3-candlefix` from `fix/v0.3-restore-integrity` (`db1730d`); its PR merges into that branch so the
restore fix stays a separately reviewable commit.

CandleFix lets a maker record a defect they saw on a batch, work through built-in **things to check**, write their own
**hypotheses**, and follow a hypothesis with a **corrective experiment**: a follow-up batch (usually from a new formula
version) and its burn tests, shown **before and after** next to the original.

## Principles

1. **Observations stay apart from ideas.** What the maker saw (issues, notes, photos) is one block. Things to check are a
   prompt list, never a diagnosis. Hypotheses are the maker's own words, always labelled "Hypothesis", in their own
   visually separate block. Nothing in the app names a cause, a fix or a verdict.
2. **History is never silently rewritten.** An investigation's batch, an experiment's investigation, hypothesis and
   follow-up batch are fixed at creation. A checked item keeps the text it had when it was ticked. A record another
   record depends on can be removed only after the dependant is removed, and every cascade is confirmed with counts.
3. **Reuse.** Batches keep their immutable `formulaId`/`versionId`, so the exact formula version of an investigation is
   the batch's. Photos reuse the BurnMatrix pipeline (`@/lib/photos`, JPEG ≤ 1 MiB, ≤ 1600 px, SHA-256, base64 in
   backups). Burn figures reuse `@/lib/burnmatrix`. Restore integrity reuses `src/lib/backup/integrity.ts`.

## Data model (schema 6)

New types in `src/lib/types.ts`; schemas in `src/lib/schemas/candlefix.ts`.

```ts
FIX_ISSUES = ["frosting", "tunneling", "sinkhole", "soot", "weakColdThrow", "weakHotThrow",
              "wetSpots", "cracking", "mushrooming", "other"]
HYPOTHESIS_STATUSES = ["open", "testing", "fits", "doesNotFit", "setAside"]

ChecklistTick = {            // one "thing to check" the maker ticked or noted
  itemId: string;            // stable built-in id "<issue>.<slug>", 1–80 chars, [a-zA-Z0-9.-]
  issue: FixIssue;           // the issue whose list it came from
  label: string;             // the item's text when first saved (snapshot, 1–200)
  checked: boolean;
  note?: string;             // ≤ 500
}

Hypothesis = {               // embedded in the investigation
  id: uuid;                  // stable; experiments point at it
  text: string;              // 1–500, the maker's own words
  status: HypothesisStatus;  // maker-set, neutral words only
  notes?: string;            // ≤ 2000
  createdAt; updatedAt;      // updatedAt moves only when text, status or notes change
}

Investigation = {            // store `investigations`
  id: uuid;
  batchId: uuid;             // fixed at creation; the exact version is the batch's
  observedOn: YYYY-MM-DD;    // never before the batch's production date (data layer)
  title?: string;            // 1–60
  issues: FixIssue[];        // 1–10, unique, stored in FIX_ISSUES order
  otherIssue?: string;       // 1–80, present exactly when issues has "other"
  notes?: string;            // observation notes, ≤ 2000
  checks: ChecklistTick[];   // ≤ 200, unique itemId
  hypotheses: Hypothesis[];  // ≤ 20, unique id, maker's order
  archivedAt: timestamp | null;
  createdAt; updatedAt;
}

InvestigationPhoto = {       // store `investigationPhotos`, write-once
  id, investigationId, mimeType "image/jpeg", width, height, byteLength, sha256, caption?, createdAt, bytes
}                            // same fields and limits as BurnPhoto; at most 12 per investigation

CorrectiveExperiment = {     // store `correctiveExperiments`
  id: uuid;
  investigationId: uuid;     // fixed
  hypothesisId: uuid;        // fixed; a hypothesis of that investigation
  followUpBatchId: uuid;     // fixed; any batch except the investigation's own
  burnSessionIds: uuid[];    // 0–8, unique, burn tests of the follow-up batch (editable)
  change?: string;           // what the maker changed, ≤ 500
  notes?: string;            // ≤ 2000
  createdAt; updatedAt;
}
```

Why a separate experiments store rather than embedding: a batch must be refused deletion while it is a follow-up, and a
burn test while an experiment lists it. Indexes answer both directly; an embedded array would need a scan of every
investigation.

### Dexie schema 6 (IndexedDB version 60)

```ts
SCHEMA_V6_ADDED = {
  investigations: "id, batchId, observedOn",
  investigationPhotos: "id, investigationId",
  correctiveExperiments: "id, investigationId, followUpBatchId, *burnSessionIds",
}
```

Only stores are added. No existing record moves, so a schema 5 database opens with all its data and three empty stores.
`SCHEMA_VERSION` 6; `APP_VERSION` stays 0.3.0 (same release line).

## Repositories (`@/lib/db`)

| Repo | Operations |
| --- | --- |
| `investigations` | `list({includeArchived})`, `listByBatch(batchId)` (archived included), `get(id)` → detail with batch, formula, version, photo count, experiments; `create` (idempotent by id), `update`, `setArchived`, `deletionImpact` → `{photos, experiments}`, `delete`, `followUpLinks(batchId)` (experiments whose follow-up is this batch, with their investigation and original batch), `comparison(id)` → everything the before-and-after view needs, in one read transaction |
| `investigationPhotos` | `listByInvestigation`, `add` (idempotent by id, ≤ 12), `delete`, `usage` |
| `correctiveExperiments` | `listByInvestigation`, `get`, `create` (idempotent by id), `update` (burn tests, change, notes only), `delete` |

Write rules (each a `DataError`):
- `invalid`: issues empty/duplicated/unknown, `otherIssue` without "other" (or missing with it), observed date before the
  batch's production date (on create, or when the date changes; a stored date is kept as it is, like M-2), unknown
  hypothesis on an experiment, follow-up equal to the original batch, a listed burn test of another batch.
- `in-use`: removing a hypothesis an experiment names (investigation update).
- `not-found`: missing batch, investigation, hypothesis, follow-up batch or burn test.
- Every write bumps `changesSinceBackup` once (DATA-13).
- `batches.update` keeps the production date at or before the earliest investigation as well as the earliest burn test.

## Archive and delete rules

| Record | Rule |
| --- | --- |
| Batch | Delete refused (`in-use`) while it has an investigation, or while it is the follow-up batch of an experiment (and still while it has burn tests, as before). `deletionImpact` adds `investigations` and `followUpExperiments` so the screen can say why. |
| Burn test | Delete refused (`in-use`) while an experiment lists it. `deletionImpact` adds `experiments`. Remove it from the experiment first. |
| Investigation | Can be archived (hidden from the all-investigations list unless "Show archived"; still on its batch page with an Archived badge, still editable). Delete removes its photos and its experiments in one transaction, after a confirmation that counts both. Follow-up batches and burn tests are not touched. |
| Hypothesis | Removed by editing the investigation; refused while an experiment names it. |
| Experiment | Deleted alone after confirmation; its follow-up batch and burn tests stay. |
| Photo | Write-once; deleted one at a time after confirmation (as BurnMatrix). |

Nothing is deleted by a cascade the maker was not shown.

## Backup format 6

- `DATA_STORES` gains `investigations`, `investigationPhotos`, `correctiveExperiments` (appended). `BACKUP_FORMAT_VERSION`
  6. Photos are stored in their backup form (base64 + SHA-256), checked by the same `checkPhotoData`.
- `checkBackupText` reads formats 1 to 6: each format is checked against its own shape and checksum, then the stores it
  lacks are added empty (format 5 gains the three CandleFix stores). Orphan counting (device ids count, mode unknown)
  adds `investigations` (batch), `investigationPhotos` (investigation) and `correctiveExperiments` (investigation,
  follow-up batch, listed burn tests).
- `planRestore`: the three stores are editable records classified whole (`canonicalJson`); photos without their bytes,
  as burn photos.
- **Integrity (`integrity.ts`), new required links:**
  - investigation → its batch (`batch-missing`)
  - investigation photo → its investigation (`investigation-missing`)
  - experiment → its investigation (`investigation-missing`)
  - experiment → a hypothesis of that investigation (`hypothesis-missing`)
  - experiment → its follow-up batch (`follow-up-missing`), which is not the investigation's own batch (`follow-up-is-original`)
  - experiment → each listed burn test exists (`listed-session-missing`) and is of the follow-up batch (`session-of-other-batch`)
  Replace needs them in the file; Merge may use the device's records, and a merge that keeps the device's copy of an
  investigation while the file's experiment names a hypothesis only the file's copy has is refused.
- **Soft, unchecked:** a check item's id against the current built-in lists (an older or newer app may have other
  items; the label snapshot keeps them readable). The observed-date rule is not checked on restore (like burn tests).

## Photos

One pipeline: `preparePhoto` (unchanged) → repository `add` (JPEG check, size, SHA-256 before the transaction, owned
copy of the bytes) → backup base64. The schema's photo fields are shared (`photoFields(owner)`); `backup/photos.ts`
converts any `{ bytes }` record to and from `{ dataBase64 }`. The gallery UI (`src/components/burn/photos`) is
generalised with a small adapter prop (list/add/delete/limit) so burn tests and investigations use the same component;
burn behaviour is unchanged.

## Things to check (`src/lib/candlefix/checklists.ts`)

A fixed list per issue, 4–7 items each, written as questions to look at ("Was the container warm when poured?"), never
as causes or fixes. Ids are `<issue>.<slug>` and never change once released; text may be reworded because the tick
stores the label it was ticked with. "Other" has a short generic list (pour temperature, cure time, room conditions,
notes from earlier batches). The editor shows the lists for the issues chosen; ticks for an issue no longer chosen
stay in the record and are shown under "From issues no longer listed".

## Hypotheses

Block heading "Hypotheses (your ideas to test)". Each card is labelled "Hypothesis" with its status as a neutral pill:
Not tested yet, Being tested, Follow-up observations fit it, Follow-up observations don't fit it, Set aside. Never
"confirmed", "proven", "solved", "root cause". Observations use a plain bordered block; hypotheses use a dashed border
and a muted background so the two never read as one.

## Before-and-after view (`src/lib/candlefix/comparison.ts`)

`investigations.comparison(id)` reads, in one transaction: the investigation, its original batch item, the original
batch's burn tests, every experiment with its follow-up batch item, its listed burn tests and the investigations
recorded on the follow-up batch. The pure `buildBeforeAfter` model turns that into columns (original first, then one
per experiment, in creation order) and rows: batch, formula and version number, production date, the hypothesis
tested, the change noted, issues observed on that batch, and per batch the burn figures from `@/lib/burnmatrix`
(burn tests, total burn time, average weight loss per hour, last melt pool diameter, largest flame height, soot seen).
Missing figures are "Not recorded". No row is coloured as better or worse. At 375px the columns become stacked cards.

`buildTimeline` lists the dated events: batch made, issue observed, hypothesis added, follow-up batch made, burn tests,
in date order (ties by kind, then id).

## Acceptance

- A batch's investigation records issues, notes, up to 12 photos, ticked things to check and hypotheses; reopens intact.
- A hypothesis links to a follow-up batch and its burn tests; the before-and-after view shows both batches with versions,
  observations and burn figures, at 1280px and 375px.
- Batch delete is refused while an investigation exists or the batch is a follow-up; burn test delete is refused while
  an experiment lists it; investigation delete removes its photos and experiments after a counted confirmation.
- A schema 5 database upgrades with every record intact; format 1–5 backups restore; a format 6 backup with
  investigation photos round-trips byte for byte; restores that break any new link are refused.
