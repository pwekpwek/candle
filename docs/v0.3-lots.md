# CandleLab Studio v0.3 — Lots, suppliers, batch search, filters and export

Scope: the first v0.3 item in the vault Tasks note. "Extend BatchTrace with material lot codes, suppliers, search, filters, and export. Verify that multiple batches from one formula can be traced independently." Built on v0.2 (`docs/v0.2-batchtrace.md`, `docs/v0.2-curepilot.md`, `docs/v0.2-burnmatrix.md`, `docs/v0.2-integration-qa.md`).

Out of scope (later v0.3 slices): CandleFix, TrueCandle Cost, the full traceability export (versions, lots, tests, defects and costs together, v0.3 integration QA), stock levels.

Branch `feat/v0.3-lots`, from `feat/v0.2-integration` (`c922234`). Its PR merges into `feat/v0.2-integration`.

## Owner-approved defaults

- **Suppliers:** their own list, with a name and optional contact notes, kept on the device only.
- **Lots:** a lot belongs to one material and optionally one supplier. It has a lot code, a received date and notes. Once a batch uses a lot, the lot can only be archived, never deleted.
- **Lots on batches:** optional per component (wax rows, each oil, wick, vessel), so existing batches stay valid. The batch stores the lot id plus a snapshot of the lot code and supplier name at the time.
- **No stock tracking:** no quantities or stock levels.
- **Search:** one box over batch label, formula name, lot code and supplier name.
- **Filters:** formula, production date range, lot or supplier, has cure plan, has burn tests. Search and filter state lives in the URL.
- **Export:** a CSV of the filtered batch list with versions and lots.

## Data model

Types in `src/lib/types.ts`, schemas in `src/lib/schemas/lots.ts` and `src/lib/schemas/batch.ts`.

### `Supplier` (store `suppliers`)

```
Supplier = {
  id: string                 // UUID made on the device
  name: string               // 1 to 80 characters after trimming
  notes?: string             // contact notes, up to 2000 characters
  createdAt, updatedAt: string
  archivedAt: string | null  // archived = hidden from pickers for new choices
}
```

### `MaterialLot` (store `materialLots`)

```
MaterialLot = {
  id: string
  materialId: string         // fixed at creation; a library material of any type
  supplierId: string | null  // a supplier, or none
  code: string               // the lot code, 1 to 60 characters after trimming
  receivedOn?: string        // YYYY-MM-DD, local calendar, optional
  notes?: string             // up to 2000 characters
  createdAt, updatedAt: string
  archivedAt: string | null
}
```

- **The material is fixed.** A batch only links a lot whose material is the material its version used for that component, so changing a lot's material would break links. `materialLots.update` refuses a different `materialId` (`invalid`), as `materials.update` refuses a type change.
- **Received date is optional.** The default says a lot "has a received date". Makers do not always know it for stock they already hold, so a blank date is allowed. The screens refuse a future date; the data layer checks the format only (the same split as production dates).
- **Codes:** two lots of one material from one supplier (or both without a supplier) may not share a code, compared trimmed and case-insensitive. The screens show this as a field error and the data layer refuses it (`invalid`). A restore can still bring two such lots together; nothing breaks, and the list shows both.
- **Supplier names** are unique the same way (trimmed, case-insensitive), archived ones included.

### Lots on a batch: `Batch.lots`

```
Batch = { …v0.2 fields…, lots?: BatchLot[] }   // absent when no lot is recorded

BatchLot = {
  part: "row" | "wick" | "vessel"
  componentId?: string       // present exactly when part is "row": a wax or oil row of the version
  lotId: string
  lotCode: string            // snapshot of the lot's code when it was linked
  supplierId: string | null  // snapshot of the lot's supplier when it was linked
  supplierName?: string      // snapshot of that supplier's name, absent without a supplier
}
```

- `lots` is optional and left out when empty, so every v0.2 batch is still valid as stored and in older backup files. Schema 5 moves no records.
- At most one lot per component: wax and oil rows are keyed by `componentId`, the wick and vessel by `part`. Stored in the version's order (waxes, oils, wick, vessel), so two copies of the same links compare equal.
- **Checks on create and update** (`invalid` unless noted): the component must exist in the batch's version (a wax or oil row; the version has a wick; the version has a vessel); the lot must exist (`not-found`) and belong to that component's material; a new link to an archived lot is refused.
- `BatchInput.lots` is optional. On `update`, leaving it out keeps the stored links as they are (callers written before v0.3 keep working); `[]` clears them.

### What an edited lot or supplier does to batches

Batch snapshots never change by themselves, as version material snapshots never do (DATA-03, DATA-11):

| Event | Batches that link the lot |
| --- | --- |
| Lot code edited | The batch keeps the code it recorded. The batch page shows "Lot now recorded as …" under it. Search matches both the recorded and the current code. |
| Lot's supplier changed, or the supplier renamed | The batch keeps the supplier name it recorded, with the same hint when it differs now. Search and the supplier filter match both the recorded and the current supplier. |
| Lot archived | The link and snapshot stay. The batch page shows an "Archived" badge. Saving the batch again keeps the link; the picker hides archived lots for new choices. |
| Supplier archived | Lots and batches unchanged. The lot form hides archived suppliers for new choices but keeps the current one. |
| Batch saved again with the same lot on a component | The stored snapshot is kept (as BurnMatrix keeps a wick's name). |
| Batch saved with a different lot on a component, or a new link | A fresh snapshot is taken from the lot and its supplier as they are now. |

To refresh a snapshot after correcting a typo, the maker clears the lot on the batch, saves, then links it again. Recorded as a possible later convenience.

The material's own free-text `supplier` field (v0.1) stays as it is: a note on the library material. The supplier list is separate and is what lots use. Merging the two is an owner decision for later.

## Archive and delete

| Record | Archive | Delete |
| --- | --- | --- |
| Supplier | Always allowed, reversible | Refused with `in-use` while any lot names it or any batch snapshot names it (`suppliers.usage`) |
| Lot | Always allowed, reversible | Refused with `in-use` while any batch links it (`materialLots.usage`) |
| Material | Unchanged rule (archive only). Its lots stay and keep working on batches. New lots can be added only for materials that are not archived. | — |
| Batch | — | Unchanged rules. Its lot links go with it; lots and suppliers are untouched. |

Delete is offered on the screens only for unused suppliers and lots, after confirmation, so a typo can be removed.

## Storage: IndexedDB schema 5

```
version(1)  v0.1 stores (unchanged)
version(2)  + batches: "id, formulaId, versionId, producedOn"
version(3)  + curePlans: "id"
            + productionPlans: "id, formulaId, versionId, plannedOn, batchId"
version(4)  + burnSessions: "id, batchId, milestoneId, testedOn"
            + burnPhotos: "id, sessionId"
version(5)  + suppliers: "id, name"
            + materialLots: "id, materialId, supplierId"
```

Schema 5 only adds two stores (IndexedDB version 50), so the upgrade moves no records (DATA-29). The batch's `lots` field is optional, so a schema 4 batch is already a valid schema 5 batch. `supplierId` null is left out of its index, which is what "lots of this supplier" wants. Tested from a real schema 4 database in `tests/unit/db/upgrade.test.ts` and with a real browser profile (handoff note).

**Indexes and search.** Search and filters run in memory over one read of the batch list (`batchTrace.read`). A maker's device holds hundreds to a few thousand batches, so one read plus a filter is fast and keeps one code path for search, filters and export. Lot-in-use checks scan `batches` (a multi-entry index cannot reach `lots[].lotId` inside objects, and a duplicated `lotIds` field is not worth a migration at this size). The two new indexes serve the lot list by material and the supplier's lot count.

## Writes and the change counter

Every write is one transaction that includes `meta` and adds 1 to `changesSinceBackup` (DATA-13): `suppliers.create / update / setArchived / delete`, `materialLots.create / update / setArchived / delete`, and `batches.create / update` (lot links are part of the batch write, one bump).

## Backup format 5

- Export writes `formatVersion: 5`, `schemaVersion: 5`, `appVersion: "0.3.0"`, with `data.suppliers` and `data.materialLots` and their counts. The checksum covers all eleven arrays.
- Restore reads formats **1 to 5**. Formats 1 to 4 are checked against their own strict shape, and their batches against the v0.2 batch shape (no `lots`), so a format 4 file whose batch carries lots is refused as damaged. Their checksum is verified over the data exactly as written; only then are `suppliers` and `materialLots` added empty in memory. A format 5 file without `suppliers` is refused as damaged. The v0.2 app refuses a format 5 file as "made by a newer version".
- Classification: suppliers and lots are editable records, compared whole (canonical JSON), and follow the maker's keep-or-replace choice. Batches are compared whole as before, so their lot links are part of the comparison. Restoring the same file twice changes nothing. "Replace everything" clears all eleven stores, and the safety backup includes them.

### Orphan checks (Step 1, refuse the whole file)

Added to the v0.2 list. `DeviceIds` gains `materialIds`, `supplierIds` and `lotIds`.

- A lot whose material is neither in the file nor on the device.
- A lot whose supplier (when set) is neither in the file nor on the device.
- A batch with a lot link whose lot is neither in the file nor on the device.

Not checked, as soft links whose names are snapshotted: a batch snapshot's `supplierId`, and whether a linked lot's material matches the batch's version (only a hand-edited file can break it; recorded with L-1).

### Interrupted or failed restore

Unchanged: one transaction over the eleven data stores and meta, the stale check inside it, and counts compared after commit.

## Search, filters and URL state (`src/lib/batchtrace`, contract in `contract.ts`)

Pure logic. The data comes from `batchTrace.read()`: every batch with its formula, version, whether it has a cure plan, its burn test count, and each lot link with the lot and supplier as they are now (null when missing).

- **Search** (`q`): split on whitespace into terms; every term must match (AND). A term matches when any of these contains it, compared case- and accent-insensitive: the batch title (label, or "Batch" + id prefix), the formula name, each recorded lot code, each current lot code, each recorded supplier name, each current supplier name.
- **Filters:** formula (`formula`), production date from and to (`from`, `to`, inclusive, YYYY-MM-DD), lot (`lot`), supplier (`supplier`, recorded or current), cure plan (`cure=yes|no`), burn tests (`burn=yes|no`). All filters combine with AND. A `from` later than `to` matches nothing; the screen shows a field error.
- **URL:** `parseBatchQuery` reads these parameters and drops values it does not understand (bad dates, unknown yes/no, malformed ids). `serializeBatchQuery` writes them in a fixed order and leaves out empty ones, so the empty query is `/batches`. The list uses `router.replace` (no history entry per keystroke or filter change), so reload keeps the view and Back from a batch page returns to the filtered list.
- The list order stays the data layer's: latest production date first.

## CSV export

`buildBatchCsv(items)`: RFC 4180 with CRLF and a UTF-8 BOM, the same quoting and formula-injection guard as the burn test CSV (cells starting with `=`, `+`, `-`, `@`, tab or CR get a leading apostrophe). Headers come from `MESSAGES.batchCsv`. File name `candlelab-batches-YYYYMMDD.csv` (device local date). It exports exactly the filtered list on screen, in its order.

One row per component of each batch's version (waxes, oils, then wick and vessel when the version has them):

| Column | Value |
| --- | --- |
| Batch | Title (label, or "Batch" + id prefix) |
| Batch ID | Full UUID |
| Production date | YYYY-MM-DD |
| Formula | Formula name now |
| Version | Version number |
| Component | Wax, Fragrance oil, Wick or Vessel |
| Material | The version's material snapshot name |
| Planned (g) | The version's stored target, at its precision (wax and oil rows) |
| Measured (g) | The batch's measured weight, when entered (wax and oil rows) |
| Lot code | As recorded on the batch |
| Supplier | As recorded on the batch |
| Lot received | The lot's received date now, when known |
| Cure plan | Yes or No |
| Burn tests | Count |

## Found and fixed during testing

- At 375px the batch form's "Add a lot" link was 18 px tall (inline in a sentence). It is now its own 44 px link under the hint.
- On the batch page, a long lot code, supplier name or "now recorded as" hint made the page wider than a 375px screen. Those lines now wrap anywhere.

## Review notes and open issues (Low)

No Critical, High or Medium finding is open. Recorded for the owner:

- **LT-1:** two filter changes on `/batches` within a few milliseconds can drop the first, because the second is built from the URL before the first `router.replace` lands. A person cannot change two controls that fast; the browser tests wait for the URL between changes.
- **LT-2:** refreshing a batch's recorded lot code or supplier name after correcting a typo needs clear, save, link again (snapshots never change by themselves).
- **LT-3:** the material's v0.1 free-text `supplier` field and the new supplier list are separate. Whether to merge them is an owner decision.
- **LT-4:** lot-in-use and supplier-in-use checks scan all batches. That is fine at the expected size (hundreds to a few thousand batches); a denormalised index would need a migration.
- **LT-5:** a restore does not check that a linked lot's material matches the batch's component (only a hand-edited file can break it), and a batch snapshot's `supplierId` is soft. Same class as L-1 in `docs/v0.2-integration-qa.md`.
- **LT-6:** the screens compare names and codes with `toLowerCase`, the data layer with `toLocaleLowerCase`. They differ only for a few locale-specific letters (for example Turkish dotted I); the data layer still refuses a real duplicate.
- **LT-7:** "Show archived" checkboxes are 16 px; their labels are the 44 px tap target.
- All wording added in this slice is marked `WRITTEN HERE (v0.3 lots)` in `src/lib/messages.ts` and needs the owner's review.
